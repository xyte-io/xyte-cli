Remediation

Guided remediation.

Use this after triage shows a real problem and an operator needs help moving from "what is wrong?" to "what can we safely do next?"

Use whenA real incident needs an approved command, note, ticket update, or close action.
InputsAn incident, device, room, ticket, or symptom the operator wants to act on.
OutputA planned action, an applied response, and a read-back check.

Ask an agent

Ask for help with the issue, not for an endpoint call. The workflow keeps the write behind an approval gate.

Help me remediate the current issue.

Use the ready tenant, or ask which tenant if more than one is ready.
Show active incidents and likely affected devices first.
If the target is unclear, show candidates and ask me to pick one.
Then show the remediation plan, available device commands, and the read-back check.
Do not apply anything until I approve the plan.

Workflow

  1. TriggerReal issueStart from an incident, room, ticket, device, or symptom.
  2. FindResolve targetSearch matching records and ask when several targets fit.
  3. PlanGate writesList available actions and stop at the plan.
  4. ApproveApply one stepRun the write only after explicit approval.
  5. ConfirmRead backCheck tenant state before closing the loop.

Goal

Remediation is not just "send a command." The useful sequence is: inspect, confirm the available action, apply only after approval, and read the state back.

Commands

  1. Start with the flow plan

    The plan shows required context and where the workflow will pause before a write.

    xyte-cli flow run flow.guided-remediation \
  --tenant <tenant-id> \
  --plan \
  --var device_id=<device-id> \
  --var incident_id=<incident-id> \
  --once \
  --strict-json

  2. List commands the device actually supports

    Choose from returned commands. Do not guess a command name from another device model.

    xyte-cli api call organization.commands.getCommands \
  --tenant <tenant-id> \
  --path-json '{"device_id":"<device-id>"}' \
  --query-json '{"page":1,"per_page":20}'

  3. Apply the approved step

    Resume the planned run only after the operator approves the write.

    xyte-cli flow run flow.guided-remediation \
  --tenant <tenant-id> \
  --apply \
  --resume <run-id-or-path> \
  --strict-json

  4. Read back the state

    Use a read command after the write so the final answer is based on tenant state, not just command submission.

    xyte-cli api call organization.devices.getDevice \
  --tenant <tenant-id> \
  --path-json '{"device_id":"<device-id>"}'

xyte-cli ops watch incidents \
  --tenant <tenant-id> \
  --profile incidents-active \
  --once

Approval gate

For write-capable workflows, show the plan result first. Apply only when a human explicitly approves the next action and the target ids are known.

{
  "status": "pending_gate",
  "nextAction": "Review command and resume with --apply",
  "requiresWrite": true,
  "resume": "xyte-cli flow run flow.guided-remediation --tenant <tenant-id> --apply --resume <run-id-or-path>"
}

You are done when the applied step has a successful response and a follow-up read command confirms the device or incident state.

If it fails

No command is available

Stop. Choose a different remediation path or escalate to a human operator.

The write response is not successful

Do not continue the loop. Inspect the endpoint response and rerun triage.

Read-back does not match the expected change

Treat the action as incomplete and include the read-back result in the handoff.
